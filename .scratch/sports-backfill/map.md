# 10-Year Sports Data Backfill Architecture (Map)

## Destination

A plan — not execution — for a Sidekiq-queue-parallelized architecture (hosted on Kubernetes, per the original ask — see ticket 01's reconsideration for why the parallelism mechanism itself is queue-based rather than native k8s `Job` fan-out) to Backfill 10 years of core game data (schedules, box scores, play-by-play, team/player stats) into Postgres for all three Backends (football, nba, mlb), including designing nba's and mlb's currently-nonexistent ingestion jobs layer. Sequenced football-first; targets the `stage` DOKS cluster; must support resuming a partially-failed run without a full re-scrape.

**Time target (revised — the original "hours or less" blanket figure wasn't realistic once source rate limits were researched)**: football completes in hours; nba within half a day; mlb within a day. nba and mlb run concurrently with each other once both are built (independent rate budgets, separate domains), so their combined wall-clock is the longer of the two (~a day), not the sum.

## Notes

- Domain: see `CONTEXT.md` at the repo root (Backend, League, Backfill, Backfill Task) — keep it updated as new terms surface.
- Related repo: `sports-app-infra` (sibling directory) holds the Kubernetes/Terraform/Ansible building blocks — DOKS clusters (`stage`, `prod`), `Runners::Cluster`, the crawler's existing Deployment+HPA. Its own `CONTEXT.md` documents Environment/Runner/Command vocabulary.
- Data breadth is fixed: schedules, box scores, play-by-play, team/player stats only. Betting lines, weather, forecasts, lineups, and advanced stats are out of scope (see below).
- Rollout is sequenced: football (already has a live ingestion pattern to extend) proves out the backfill approach before nba/mlb's from-scratch jobs layer is designed against it.
- Grilling-heavy effort — call the `grilling` skill (and `domain-modeling` if new vocabulary surfaces) for every ticket unless it's explicitly typed `research`.

## Decisions so far

- [Research: stage DOKS cluster's current capacity and headroom](issues/03-stage-cluster-capacity.md) — stage is provisioned identically to prod (not downsized): a single `s-4vcpu-8gb` node pool autoscaling 1-5 nodes, `db-s-1vcpu-1gb` Postgres. The crawler's current HPA ceiling (10 replicas) already pushes stage past 1 node; raising it could support roughly 3-4x more crawler pods before hitting the 5-node cap. Postgres connection limits and live utilization need DO console/kubectl access this research didn't attempt — flagged as an open question for whoever runs the backfill.
- [Research: source rate-limit tolerance](issues/02-source-rate-limit-tolerance.md) — Basketball-Reference/Baseball-Reference (Sports Reference LLC) publish a hard 20 req/min limit with up to 24hr IP blocks on violation — safe concurrency there is ~1-2 sessions each (independent per-domain budgets, nba and mlb don't share one pool). ESPN has no published numeric limit but shows signs of active bot mitigation; ~3-5 concurrent sessions is a cautious unverified inference. None of the three sources offers a bulk/API alternative. All three sources' terms of use separately prohibit automated scraping as a contractual matter, independent of concurrency — user has chosen to proceed despite this.
- [Revisit the backfill time target for nba/mlb given the rate-limit ceiling](issues/07-revisit-time-target.md) — revised the destination's time target per-backend (football: hours; nba: within half a day; mlb: within a day) rather than forcing the original blanket "hours" figure. Declined to increase throughput via proxies (too much added ToS/ban risk) or pursue Sports Reference's $5,000+ paid data offering (unproven effort, deferred). Scope (10 years, all three sports) unchanged. nba/mlb will run concurrently with each other once both are built, since they're independent rate budgets. **Unaffected by ticket 01's reconsideration below** — the concurrency ceilings (and so the wall-clock math) are the same whether expressed as a rate limiter or a worker-pool size.
- [Choose the Kubernetes parallelization mechanism for Backfill Tasks](issues/01-parallelism-mechanism.md) — **reopened once, see the ticket's Reconsideration section.** Originally: one Kubernetes `Job` per Backfill Task + a crawler-side Redis rate limiter. Reconsidered after a "shouldn't this be a queue worker?" challenge mid-map: switched to a **Sidekiq queue-worker model** — a fixed-size worker pool per backend (football ~3-5, nba ~1-2, mlb ~1-2) is the throttle, no crawler-side rate limiter needed. Workers self-enqueue follow-on work (football's week-count discovery, mlb's/nba's inter-task-type dependencies) instead of an external orchestrator. nba/mlb now get Sidekiq/Redis for both live and backfill, reversing part of tickets 05/06. This invalidated the k8s-Job-shaped parts of tickets 04, 05, 06, and 08 and made ticket 09 moot (closed) and ticket 10 moot (closed, absorbed into 05/06's eventual rework).
- [Design football's Backfill Task](issues/04-football-backfill-task-design.md) — **reworked** under the new Sidekiq model: a new `BackfillFootballWeekJob(league, year, week)` on a dedicated `backfill` queue reuses the existing `UpdateGameJob` unchanged (just enqueued with an overridden queue), no shared-service-object extraction needed. `week == 1`'s job is the sole owner of discovery — it self-enqueues the season's remaining weeks once it learns the count, so ticket 08's seed step only needs 30 enqueues (one per `(league, year)`), not one per week. Idempotency fix and 2016-2025 window unchanged from the original resolution.
- [Design nba's ingestion jobs layer](issues/05-nba-ingestion-jobs-design.md) — **reworked**: replaces the season-level batching with four self-enqueuing jobs mirroring the crawler's own scrape boundaries — `NbaSyncTeamsJob(year)` → enqueues `NbaSyncRosterJob(year, team)` per team and `NbaSyncScheduleJob(year)` → enqueues `NbaSyncGameStatsJob(...)` per game. Giving nba its own teams-first job resolves ticket 10's old asymmetry by matching mlb's original approach. Live mechanism drops the Rake-task layer — the CronJob enqueues `NbaSyncTeamsJob` directly via `rails runner`; live uses `:default`, backfill uses `:backfill`, same job classes for both. Idempotency fix, deployment-gap plan, and Season year convention unchanged from the original resolution.
- [Design mlb's ingestion jobs layer](issues/06-mlb-ingestion-jobs-design.md) — **reworked**: same four-job self-enqueuing shape as nba, adapted 1:1 from the legacy `Database::Builder` classes — `MlbSyncTeamsJob(year)` → enqueues `MlbSyncRosterJob(year, team)` and `MlbSyncScheduleJob(year, team)` per team (mlb's schedule is per-team, unlike nba's season-wide call) → `MlbSyncScheduleJob` enqueues `MlbSyncGameStatsJob(year, game_url)` per game. Live mechanism matches nba's (CronJob + `rails runner`, `:default`/`:backfill` split). Legacy-code-reuse, batted-ball-stats-in-scope, idempotency fix, and deployment-gap plan unchanged from the original resolution.
- [Design the Backfill Task orchestrator/dispatch layer](issues/08-orchestrator-design.md) — **reworked**: shrank to just the seed step (50 total enqueues: 30 football, 10 nba, 10 mlb) since workers now self-enqueue everything downstream. A `rake backfill:seed` task in each backend, invoked via a new `backfill_seed` method on `sports-app-infra`'s `Runners::Cluster` that does `kubectl exec <pod> -- bundle exec rake backfill:seed` — mirroring its existing `seed` method's pattern almost verbatim. No new Runner class, no `kubectl wait`/log-parsing, no workflow engine. Failure handling is now entirely Sidekiq's own retry/backoff.

- [Check football's games table for duplicate espn_id rows before the unique-index migration runs](issues/11-espn-id-duplicate-check.md) — no pre-migration check needed; existing production data is disposable. If the unique-index migration (ticket 04) fails on existing duplicates, the fix is a trivial destructive cleanup (delete duplicates, keep one per `espn_id`) rather than careful reconciliation.

Every ticket is now resolved or closed (ticket 01 was once reopened and re-resolved; 04/05/06/08 were reworked in its wake; 09/10 were closed as moot/absorbed). This map is done.

## Not yet specified

- Whether a data-validation/QA pass is needed after a backfill run (e.g. reconciling scraped game counts against each league's known schedule totals).
- Whether the multi-hour (or multi-day, for nba/mlb) run needs dedicated monitoring/alerting (Datadog already exists in `sports-app-infra`) or standard logs are enough.
- Stage's actual live utilization and Postgres connection ceiling (the capacity research could only read static Terraform config, not the live cluster/DO console) — someone with DO access needs to confirm before the chosen parallelism level is trusted at execution time.

## Out of scope

- Betting lines, weather, forecasts, lineups, and advanced Fangraphs/odds stats for any sport — "core game data" only, decided while naming the destination.
- Actually running the 10-year backfill. This map produces the plan; execution is a separate future effort.
- Postseason/playoff games for football — decided while resolving the football Backfill Task design ticket. ESPN's schedule endpoint hardcodes regular-season-only when given an explicit year; reaching playoff weeks needs a crawler-side change not taken on here. Deferred to a later effort, not this map.
